# 概念的要件定義書

## 1. 本書の位置づけ

本書は「何を・何で・どのような方針で**実装するのか**」と「何を・何で・どのような方針で**実装しないのか**」を定義する境界線の文書である。

- 本書は**実装計画ではない**（ステップ列挙・スケジュール・機能目標は記述しない）。
- 本書は**機能仕様書ではない**（達成すべき機能の詳細は記述しない）。
- 本書は実装の**採用・不採用の境界**と、その背後にある**方針・制約**を記録し、今後の判断のよりどころとする。

本書に記載のない事項は「未定義」であり、実装前に本方針との整合性を判断して追記する。

## 2. 制約条件（すべての判断の前提）

| # | 制約 | 内容 |
|---|------|------|
| C1 | ハードウェア | NVIDIA GeForce RTX 3050 Laptop GPU、**VRAM 4GB** |

## 3. 実装する事項

### 3.1 採用技術・手法

| # | 事項 | 実装手段 | 採用方針・理由 |
|---|------|---------|---------------|
| I1 | 基盤モデル | `google/gemma-3-1b-it`（Gemma 3 1B instruction 版） | 4GB VRAM で実運用可能な最小実用規模。Gemma 3 世代の日本語性能を採用する |
| I2 | 学習手法 | **QLoRA**（`load_in_4bit=True`、r=8、lora_alpha=16、lora_dropout=0） | 4GB VRAM でフルチューニングは物理的に不可能。LoRA 適用対象は投影層（q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj）のみとし、VRAM節約のため modules_to_save（embed_tokens, lm_head）は不採用 |
| I3 | 学習フレームワーク | **Unsloth 2026.7.6** + TRL `SFTTrainer` / `SFTConfig` | Unsloth ネイティブの Fast Eager パッチ・省メモリ勾配チェックポイントを全面的に信頼・活用 |
| I4 | 特殊トークン | `<|start_of_metadata|>` 等 4 種を追加し `resize_token_embeddings(pad_to_multiple_of=8)` | データ形式（metadata/story タグ）を構造化して学習に反映するため |
| I5 | メモリ制御 | `PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True,garbage_collection_threshold:0.7"` | 活性化メモリを早期解放し、空き VRAM を安定的に確保する |
| I6 | 勾配チェックポイント | Unsloth 専用 `use_gradient_checkpointing="unsloth"` | Attention 中間状態を保存せず再計算（Recomputation）し、VRAM 消費を大幅削減 |
| I7 | オプティマイザ | `adamw_8bit` | LoRA パラメータのみの更新であり 8bit 版で十分。VRAM 節約と学習安定性の両立 |
| I8 | データ読込 | `load_dataset("json", ...)` による Memory-Mapped Arrow 形式 | RAM 枯渇を完全に防ぎつつ高速に全件データを安全にイテレーション |
| I9 | キャッシュ自動隔離・自動消去 | `HF_DATASETS_CACHE` をプロジェクト内一時フォルダに隔離し `finally` で自動全消去 (`shutil.rmtree`) | ディスク領域（74GB制限）をゴミキャッシュで埋め尽くす問題を根本解決 |
| I10 | ログ・監視 | `loguru` 構造化 JSON / 色付きターミナル ＋ `TelemetryCallback` | 16進 `trace_id` による一意コンテキスト追跡とリアルタイム VRAM / 温度監視 |
| I11 | 出力形式 | 最終成果物は LoRA アダプタ + トークナイザを `gemma3-finetuned/` へ保存 | 4bit ベースモデルと組み合わせて推論・再利用できる形式 |

### 3.2 学習パラメータ（固定値）

- 1 epoch / bf16 / cosine スケジューラ / warmup 3% / max_grad_norm=0.3
- batch 1 × 勾配蓄積 8（実効バッチ 8）/ 最大シーケンス長 1024

## 4. 実装しない事項（過干渉・アンチパターンの不採用）

| # | 事項 | 不採用の手段・代替 | 不採用方針・理由 |
|---|------|-------------------|-----------------|
| X1 | Gemma 4 E2B でのファインチューニング | Gemma 3 1B に切替 | 公式要件が **VRAM 8GB** であり 4GB 環境では成立しない (C1) |
| X2 | Liger Kernel (`liger-kernel`) | Unsloth ネイティブ Fast Eager カーネルを維持 | Gemma 3 + Unsloth の組み合わせでは Liger が Unsloth の手動最適化カーネルを `flex_attention` で無断上書きし、速度 2.3 倍悪化 ＆ VRAM 増大によるオフロード再発を引き起こすため不採用 |
| X3 | 自前手動パッキング / `packing=True` | Unsloth の auto padding-free パイプラインに委譲 | 自前の Python / Arrow パッキングは CPU 処理のボトルネックを発生させ学習ループを低速化させる。またデータ分布汚染リスクがあるため不採用 |
| X4 | 手動 CPU オフロード強制遮断フラグ群 | Unsloth 既定の自動判定に委任 | `UNSLOTH_OFFLOAD_GRADIENTS=0` 等で強制無効化すると、VRAM 4GB 境界線で PyTorch アロケータの断片化やクラッシュを引き起こすため不要 |
| X5 | 手動バッチサイズ実測推定器 (`determine_optimal_batch_size`) | `bsz=1, grad_accum=8` 固定 | VRAM 4GB 環境では計算するまでもなく bsz=1 が物理的上限。Unsloth の Fused Loss LRU キャッシュを事前フォワードパスで破壊するリスクを防ぐため撤廃 |
| X6 | `paged_adamw_8bit`（ページングオプティマイザ） | `adamw_8bit` | LoRA のみの更新量（6.5M）ではページング管理のオーバーヘッドのみが加算されるため不採用 |
| X7 | フルファインチューニング | QLoRA に切替 | VRAM 4GB では物理的に成立しない |
| X8 | シーケンス長 2048 の強制適用 | `MAX_SEQ_LENGTH = 1024` | 4GB VRAM において 2048 長の計算は 1 サンプルだけで VRAM 3.7GB 以上を要求し CPU オフロード（30s/it 超）が不可避となるため不採用 |

## 5. 判断基準（今後発生する選択のよりどころ）

1. **VRAM 制約を超える方式は不採用**（C1 が最優先）。
2. **Unsloth のネイティブ最適化パイプラインに逆らわない**。外部ライブラリ（Liger等）や自前パッキング等の「過干渉」は Unsloth の高速カーネルを干渉・破壊するため排斥する。
3. **実測を根拠に採否を決める**（Liger 導入時の 2.3 倍速度悪化、手動パッキング時の CPU ボトルネックなど、数値・エラーログを基準とする）。
4. **「最先端を足せば速くなる」という過剰エンジニアリングを廃し、最小限のシンプルな構成を維持する**。
5. 本書にない新たな選択肢が現れた場合は、本書の該当項を追記・更新してから判断する。

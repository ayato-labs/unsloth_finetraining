# 概念的要件定義書

## 1. 本書の位置づけ

本書は「何を・何で・どのような方針で**実装するのか**」と「何を・何で・どのような方針で**実装しないのか**」を定義する境界線の文書である。

- 本書は**実装計画ではない**（ステップ列挙・スケジュール・機能目標は記述しない）。
- 本書は**機能仕様書ではない**（達成すべき機能の詳細は記述しない）。
- 本書は実装の**採用・不採用の境界**と、その背後にある**方針・制約**を記録し、今後の判断のよりどころとする。

本書に記載のない事項は「未定義」であり、実装前に本方針との整合性を判断して追記する。

## 3. 実装する事項

### 3.1 採用技術・手法

| # | 事項 | 実装手段 | 採用方針・理由 |
|---|------|---------|---------------|
| I1 | 基盤モデル | `google/gemma-3-1b-it`（Gemma 3 1B instruction 版） | 4GB VRAM で実運用可能な最小実用規模。Gemma 3 世代の日本語性能を採用する |
| I2 | 学習手法 | **QLoRA**（`load_in_4bit=True`、r=8、lora_alpha=16、lora_dropout=0） | 4GB VRAM でフルチューニングは物理的に不可能。LoRA 適用対象は注意・MLP 全投影層 |
| I3 | 学習フレームワーク | **Unsloth 2026.7.6** + TRL `SFTTrainer` / `SFTConfig` | 4bit 対応・省メモリ勾配チェックポイント・高速パッチが 4GB VRAM 運用の前提 |
| I4 | 特殊トークン | `<|start_of_metadata|>` 等 4 種を追加し `resize_token_embeddings(pad_to_multiple_of=8)` | データ形式（metadata/story タグ）を構造化して学習に反映するため |
| I5 | メモリ制御 | `PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True,garbage_collection_threshold:0.7"` | 活性化メモリを早期解放し、空き VRAM を安定的に確保する |
| I6 | ダブルバッファ | `UNSLOTH_DISABLE_DOUBLE_BUFFER=1` で**無効化** | VRAM 逼迫時に Unsloth の二重バッファリングが不安定化（速度 59s/it まで崩壊）するため、明示的に無効化して安定動作を優先 |
| I7 | 勾配チェックポイント | Unsloth 専用 `use_gradient_checkpointing="unsloth"`（CPU オフロード込み） | 活性化メモリを CPU へ退避する Unsloth の既定設計であり、4GB 運用の根幹として採用 |
| I8 | オプティマイザ | `adamw_8bit` | LoRA パラメータのみの更新であり 8bit 版で十分。VRAM 節約と学習安定性の両立 |
| I9 | データ読込 | `load_dataset` ストリーミング + 先頭 `MAX_SAMPLES` 行のみ取得 | 5.4GB 全体のパースによるメモリ・時間の消費を回避 |
| I10 | トークナイズ | `dataset_num_proc=1`（シングルプロセス） | 実測でマルチプロセス化が約 5 倍遅いため、並列化を採用しない |
| I11 | 評価戦略 | `eval_strategy="epoch"`（エポック末に 1 回のみ） | 500 件の eval に約 14 分を要するため、頻回評価（24 回/epoch）による時間消費を排除 |
| I12 | 保存戦略 | `save_steps=200`、`save_total_limit=2`、`load_best_model_at_end=False` | 途中クラッシュ時の全損を防ぐ。エポック末 1 回の eval ではベスト判定が無意味なため採用しない |
| I13 | 監視 | `TelemetryCallback`（20 ステップ間隔で VRAM / RAM / 温度 / クロック / 電力を出力） | サーマルスロットリングとメモリ逼迫を切り分け、異常進行を早期検知する |
| I14 | 実行形態 | `run_train.sh`（PATH 設定 + `PYTHONUNBUFFERED=1`）+ tmux デタッチセッション | WSL セッション終了時のプロセス死を防ぎ、リアルタイムログ（`train_run2.log`）を確保する |
| I15 | 出力形式 | 最終成果物は LoRA アダプタ + トークナイザを `gemma3-finetuned/` へ保存 | 4bit ベースモデルと組み合わせて推論・再利用できる形式 |

### 3.2 学習パラメータ（固定値）

- 1 epoch / bf16 / cosine スケジューラ / warmup 3% / max_grad_norm=0.3
- batch 1 × 勾配蓄積 8（実効バッチ 8）/ 最大シーケンス長 2048 / 総ステップ 1,188

## 4. 実装しない事項

| # | 事項 | 不採用の手段・代替 | 不採用方針・理由 |
|---|------|-------------------|-----------------|
| X1 | Gemma 4 E2B でのファインチューニング | Gemma 3 1B に切替 | 公式要件が **VRAM 8GB** であり 4GB 環境では成立しない。ハードウェア制約 (C1) を超える方式は採用しない |
| X2 | フルファインチューニング | QLoRA に切替 | VRAM 4GB では重み・勾配・オプティマイザ状態が収まらない |
| X3 | 埋め込み層のカスタム CPU オフロード | 独自 forward フックでの該当行のみ gather | Gemma 3 は `embed_tokens` と `lm_head` が**重み共有**のため、CPU 化すると GPU 演算で RuntimeError が発生する。PEFT `modules_to_save` との競合リスクもあり、**最終手段としてのみ検討**する |
| X4 | Unsloth 公式の `train_embed_tokens` / `train_lm_head`（`modules_to_save` 方式） | `target_modules` を投影層のみに限定 | 学習用 fp32 コピーが GPU に常駐し、VRAM 削減目的に反するため |
| X5 | 学習データの削減・変更（`MAX_SAMPLES`・シーケンス長の縮小） | 現行値（10000 件 / 2048 token）を維持 | ユーザー方針 (C3, C4)。VRAM 問題はデータ変更ではなくメモリ制御（I5-I7）で解決する |
| X6 | ダブルバッファの有効化（空き VRAM に応じた自動有効化への依存） | `UNSLOTH_DISABLE_DOUBLE_BUFFER=1` | 空き VRAM >512MB 条件の維持は脆弱で、条件崩壊時に 10s/it → 59s/it へ劣化する実績がある。条件依存の最適化は採用しない |
| X7 | eval の頻回実行（`eval_steps=50/200` 等） | エポック末 1 回 | eval 500 件 × ~14 分のコストが全体の数時間を占有するため |
| X8 | `load_best_model_at_end=True` | `False` に固定 | eval と保存戦略の不一致でバリデーションエラーになり、かつエポック末 1 回の eval では意味がない |
| X9 | `paged_adamw_8bit`（ページングオプティマイザ） | `adamw_8bit` | LoRA のみの更新量ではオプティマイザ状態が微小で効果がない |
| X10 | マルチプロセストークナイゼーション | `dataset_num_proc=1` | 実測で約 5 倍遅い。並列化のための並列化は行わない |
| X11 | `warmup_ratio` の使用 | `warmup_steps` を明示算出 | 将来の transformers バージョンでの削除予定のため、現行 API で安定する方式を採用 |
| X12 | CPU 勾配オフロードの無効化 | なし（Unsloth 既定動作のため制御不可） | ソースコード上、2MB 超の活性化を常時 CPU に退避する既定設計であり、これを止める手段が存在しないため対象外 |

## 5. 判断基準（今後発生する選択のよりどころ）

1. **VRAM 制約を超える方式は不採用**（C1 が最優先）。
2. **データを犠牲にしない**（C3, C4）。問題解決はメモリ制御・実行方式・監視の側で行う。
3. **既存フレームワークの既定設計に逆らわない**（Unsloth の CPU オフロードやダブルバッファの仕様に抗うカスタム実装は、検証済みの理由がある場合のみ）。
4. **実測を根拠に採否を決める**（トークナイズ並列化の実測 5 倍遅延、ダブルバッファ崩壊時の速度劣化など、数値を基準とする）。
5. **過程より安定性**：速度向上が安定動作を脅かす場合は、安定動作を優先して速度機能を切り捨てる（I6 の例）。
6. 本書にない新たな選択肢が現れた場合は、本書の該当項を追記・更新してから判断する。
